- 200종목을 동시에 돌려도 매분 처리가 1초 CPU에 한참 못 미치게 합니다.

## 1. 증분 피처 프레임

### 1.1 원리

이전에는 운영 봇이 매분 1분봉 프레임 전체(1,500봉, 61열)를 다시 계산했습니다. 5분·15분·1시간 프레임도 각 봉이 마감될 때마다 다시 계산했습니다.

이제는 `heartless/data/incremental.py`의 `IncrementalFrame`이 새 봉 하나의 행만 계산합니다.

- **재귀 필터**(EMA, Wilder ATR·RSI·ADX, MACD 시그널, 슈퍼트렌드, 세션 VWAP, 스퀴즈 연속 봉 수): `indicators.py`의 반복문과 같은 Python float 연산을 같은 순서로 이어 갑니다.
- **누적합 창**(SMA, 롤링 합: 볼린저 중심선, 거래량 SMA·z, 테이커 비율, CVD, 초피니스, 허스트의 q-합): 배치와 같은 `np.cumsum` 누계를 들고 있다가 `(C[i+1] - C[i+1-n]) / n`을 같은 숫자로 계산합니다.
- **창 축약**(롤링 표준편차·최대·최소, 백분위 순위, 회귀 기울기, 허스트 분산): 마지막 창 하나에 같은 numpy 축약을 씁니다. numpy는 배치의 창 뷰를 행마다 독립적으로 축약하므로 결과가 같습니다.
- **리샘플**: 1분봉이 5분·15분·1시간·4시간·1일 그룹을 완성하면, 그 그룹을 `candles.resample()`과 같은 방법(같은 1분봉에 `np.*.reduceat`, 마지막 그룹의 같은 완결 규칙)으로 묶어 그 프레임에 한 행을 붙입니다.

`indicators.py`의 지표 가운데 증분으로 비트 동일하게 만들 수 없는 것은 없었습니다. 그래서 배치로 남긴 지표가 없습니다.

### 1.2 "비트 단위로 같다"의 정의

증분 프레임은 **앵커 이후의 봉 전체에 대한 배치 계산** `FeatureFrame(tf, 앵커 이후 봉)`과 열마다 비트 단위로 같습니다. NaN 위치도 같고, 나머지 값은 IEEE-754 비트까지 같습니다.

- 앵커는 프레임을 마지막으로 통째로 만든 시점의 첫 봉입니다.
- 앵커가 중요한 이유: 배치 결과는 프레임이 어디서 시작하는지에 따라 달라집니다(EMA 시드, 누적합).
- 그래서 이전 운영 경로(매분 마지막 1,500봉으로 다시 계산 = 앵커가 매분 한 칸씩 이동)와는 비트 단위로 같을 수 없습니다. 차이의 크기는 1.5절에 있습니다.

### 1.3 재앵커와 자가 점검

프레임은 일정 행 수가 붙으면 다시 만들어집니다(`REANCHOR_ROWS`).

| 프레임 | 재앵커 주기 | 프레임 행 수 증가 |
|---|---|---|
| 1m | 240행 (4시간) | +16% |
| 5m | 96행 (8시간) | +10% |
| 15m | 32행 (8시간) | +5% |
| 1h | 24행 (하루) | +5% |

- 다시 만들기 직전에 증분 열 전체를 같은 봉에 대한 배치 재계산과 비교합니다.
- 같으면 1분봉 꼬리로 프레임을 다시 만듭니다. 이것은 이전 매분 재계산과 정확히 같은 프레임입니다.
- 다르면 오류 로그를 남기고 그 종목만 이전 방식(매 봉 배치 재계산)으로 돌아갑니다. `/health`의 `features` 줄에 그 수가 나옵니다.
- 종목마다 첫 재앵커 시점을 심볼 해시로 흩어 놓아, 200종목이 같은 분에 몰리지 않게 했습니다.
- 재앵커는 누적합이 앵커에서 멀어지며 정밀도를 잃는 것도 막습니다.

다음 경우에는 그 자리에서 전체를 다시 만듭니다(작업 스레드에서).

- 1분봉 배열이 교체된 경우
- 저장된 봉이 고쳐진 경우: 값이 다른 같은 시각의 봉, 마지막 봉보다 앞선 봉의 삽입. 같은 봉의 중복 수신은 고친 것으로 보지 않습니다.
- 이를 위해 `CandleArrays.edits`·`trims` 카운터를 추가했습니다.

### 1.4 4시간·1일 프레임

4시간·1일 프레임은 원래부터 1분봉 이력 전체를 앵커로 씁니다. 증분 경로는 이 앵커를 그대로 지킵니다.

- 이력이 매일 자정에 잘리면(`_trim_history`), 그 프레임은 다음 봉이 마감될 때 다시 만듭니다. 이전 경로가 다시 만들던 바로 그 순간입니다. 이때 자기가 들고 있던 봉을 재사용하므로 1분봉 전체를 다시 리샘플하지 않습니다.
- 그래서 4시간·1일 프레임은 **모든 시점에서 이전 경로와 비트 단위로 같습니다**. 테스트가 매분 비교합니다.

### 1.5 이전 운영 경로(슬라이딩 창)와의 차이

같은 하루(1,440분)에서 각 기준 프레임의 최신 행을 비교했습니다(벤치마크 `--deviation`).

| 종목 | 비트 동일 값 비율 | 가장 큰 상대 차이 |
|---|---|---|
| BTCUSDT | 93.3% | 1h.ema200 1.2e-4, 15m.ema200 5.8e-6, 5m.ema200 9.0e-7, 1m.ema200 5.4e-9, 나머지 < 3e-11 |
| SOLUSDT | 96.9% | 1h.ema200 1.3e-4, 15m.ema200 1.1e-5, 나머지 < 1e-6 |
| DOGEUSDT | 97.7% | 1h.ema200 3.5e-4, 15m.ema200 4.0e-6, 나머지 < 2e-6 |

차이는 EMA200의 시드 효과뿐입니다. 1시간 창 520봉 안에서는 EMA200 시드의 무게가 약 4%(=(199/201)^320) 남습니다. 이전 경로는 매시간 다른 봉으로 시드를 잡았고, 증분 경로는 앵커의 봉으로 잡습니다.

**백테스터 값과 비교:** 백테스터는 긴 이력 전체로 계산하므로 시드 효과가 사실상 0입니다. 150일 이력으로 계산한 프레임 값을 기준으로 마지막 3일을 비교했습니다. 증분 경로가 조금 더 가까웠습니다.

| 피처 | BTCUSDT 증분 / 슬라이딩 (평균 상대오차) | DOGEUSDT 증분 / 슬라이딩 |
|---|---|---|
| 1h.ema200 | 4.3e-4 / 5.2e-4 | 6.6e-4 / 8.5e-4 |
| 15m.ema200 | 7.5e-6 / 8.4e-6 | 2.0e-5 / 2.1e-5 |
| 5m.ema200 | 3.7e-7 / 5.0e-7 | 5.3e-7 / 8.5e-7 |

참고로 1h.ema200은 두 운영 경로 모두 백테스터와 약 5e-4 차이가 납니다. 이것은 F7 이전부터 있던 차이로, 1시간 창이 520봉이라서 생깁니다. 증분 갱신은 비용이 창 길이와 무관하므로 이 창을 늘리는 것이 이제 메모리 문제일 뿐입니다(9절).

## 2. 로컬 오더북 (`ORDERBOOK_STREAM`, 기본 꺼짐)

`heartless/exchange/orderbook.py`와 `binance_ws.BookStream`이 담당합니다.

### 2.1 스트림 모드

- **partial**(기본)
  - 구독: `<symbol>@depth20@100ms`
  - 메시지마다 상위 20호가로 책을 교체합니다. REST 스냅샷이 필요 없습니다.
  - 20번째 호가 밖의 깊이는 보이지 않습니다(`levels`가 몇 호가를 봤는지 알려 줍니다).
- **diff**
  - 구독: `<symbol>@depth@100ms`
  - Binance USD-M 절차를 따릅니다.
    1. 스트림을 버퍼에 쌓습니다.
    2. REST 스냅샷(`/fapi/v1/depth`, 100호가, 가중치 5)을 받습니다.
    3. `u < lastUpdateId` 이벤트는 버립니다.
    4. 첫 이벤트는 `U ≤ lastUpdateId ≤ u`이거나 `pu == lastUpdateId`여야 합니다.
    5. 이후는 `pu == 직전 u` 사슬을 확인합니다.
    6. 이미 반영한 이벤트(중복·늦게 도착)는 무시합니다.
    7. 사슬이 끊기거나(유실·순서 뒤바뀜) 재접속하면 책을 버리고 스냅샷부터 다시 맞춥니다.
  - 재접속 때 모든 종목이 한꺼번에 스냅샷을 요청하지 않도록 0.25초 간격으로 보냅니다.
- 깊이 스트림은 1분봉 스트림과 다른 연결(연결당 50종목)을 씁니다. 1분봉 연결의 URL과 메시지량은 그대로이고, 깊이 연결이 끊겨도 봉은 끊기지 않습니다.
- 처리 비용(이 머신, 표준 json):
  - partial 20호가 메시지 해석·반영 13µs
  - diff 8+8호가 메시지 7.7µs
  - 특징 계산: partial 책 4µs, 2,000호가 diff 책 0.11ms
  - 200종목 × 초당 10메시지면 코어의 약 3%입니다.

### 2.2 알파에서 쓰기

`ctx.book`은 `BookFeatures`이며 필드는 다음과 같습니다.

| 필드 | 뜻 |
|---|---|
| `spread_bps` | (최우선 매도 − 최우선 매수) / 중간가 |
| `imbalance` | (매수 깊이 − 매도 깊이) / 합, −1 ~ 1 |
| `depth_bid_k`, `depth_ask_k` | 중간가에서 k bps 안의 호가 명목 금액(USDT). k = `ORDERBOOK_DEPTH_BPS` |
| `staleness_ms` | 책이 마지막으로 갱신된 뒤 지난 시간 |
| `mid`, `k_bps`, `levels`, `source` | 보조 정보. `source`는 `"stream"` / `"proxy"` / `"none"` |

- 책이 없으면 `EMPTY_BOOK`(값은 NaN, source `"none"`)입니다.
- 꺼져 있을 때도 운영 앱은 `ctx.book = EMPTY_BOOK`을 넣습니다.
- `book_of(ctx)`는 `ctx.book`이 없는 컨텍스트(아래 백테스터)에서도 `EMPTY_BOOK`을 돌려줍니다.

### 2.3 과거 데이터의 보수적 대용치

과거에는 호가 기록이 없습니다. 그래서 `bar_book_proxy()`가 마감된 1분봉 15개로 대용치를 만듭니다.

- **스프레드:** 1분봉 고저폭 중앙값의 20%. 최소 1틱입니다.
- **깊이:** 한쪽당 1분 거래대금 중앙값의 10%. 고저폭이 k보다 넓으면 k/고저폭만큼 줄입니다(넓은 범위 = 중간가 근처가 얇음).
- **불균형:** 0. 정보 없음으로 둡니다.
- **staleness:** 봉 마감 이후 경과 시간입니다.

유동성 있는 USD-M 무기한의 실제 호가는 이것보다 좁고 두껍습니다. 예를 들어 BTC 1분 고저폭은 수 bps라 대용 스프레드가 약 1 bp인데, 실제 스프레드는 0.02 bp 안팎입니다. 따라서 "좁고 두꺼운 호가"를 요구하는 규칙은 과거 데이터에서 운영보다 엄격하게만 작동합니다.

- **리플레이:** `ORDERBOOK_STREAM=true`이면 깊이 스트림 대신 `heartless/replay/book.py`의 `ProxyBooks`가 같은 필드 이름으로 대용치를 줍니다. 그 종목의 운영 1분봉 프레임에서 지금 이전에 마감된 봉만 씁니다.
- **백테스터:** 이번 패키지는 learning 패키지를 건드리지 않았습니다. 연결 방법은 9절에 있습니다.

## 3. 런타임

- **orjson:** 설치되어 있으면 웹소켓 메시지 해석에 씁니다(`binance_ws.JSON_ENGINE`). 없으면 표준 json입니다. 필수가 아닙니다.
  - 측정(orjson 3.13, 해석 결과는 json과 같음): kline 메시지 3.4 → 1.0µs, depth20 7.2 → 2.7µs, 600종목 markPrice 배열 333 → 212µs.
  - F7 테스트는 orjson·uvloop가 있을 때와 없을 때 모두 통과합니다.
- **uvloop:** 설치되어 있으면 `perf.loop_factory()`가 그 이벤트 루프 팩토리를 돌려줍니다. 진입점 연결 한 줄이 필요합니다(9절). 필수가 아닙니다.
- **REST 연결 재사용**
  - httpx 기본 설정은 유휴 연결을 5초 뒤에 닫았습니다. 그래서 조용한 1분 뒤의 주문은 TCP+TLS 핸드셰이크를 새로 했습니다.
  - 이제 유휴 연결을 55초 유지합니다.
  - 실거래 엔진이 붙으면 25초마다 서버 시간 요청(가중치 1)으로 연결을 데워 둡니다(`keep_warm`). 이 요청이 시계 오프셋도 갱신합니다.
- **요청 묶기**
  - 시작 때 읽는 값들을 동시에 미리 받아 두고(`BinanceRest.prefetch`), 순서대로 실행되는 기존 코드가 그 답을 한 번씩 씁니다(10초 안). 대상은 premiumIndex·fundingInfo·24h 시세·포지션 모드·계정·포지션·미체결·알고 주문입니다.
  - 실패한 요청은 저장하지 않으므로, 쓰는 쪽이 다시 보내고 오류를 직접 봅니다.
  - Binance는 시세·펀딩·미체결을 전 종목 한 번에 주는 형태로 이미 쓰고 있으므로, 더 묶을 수 있는 요청은 없었습니다.
- **시계 드리프트 감시**(`perf.DRIFT`)
  - REST 서버 시간 동기화와 스트림 이벤트 시각(1분 창의 최소 지연 = 시계 차 + 최단 네트워크 지연)을 봅니다.
  - |로컬 − 거래소|가 `CLOCK_DRIFT_WARN_MS`(1초)를 넘으면 경고 로그를 남기고, `/health`의 `clock` 줄에 보여 줍니다.
  - 서명 요청은 이미 측정된 오프셋을 싣습니다. `-1021`이면 다시 동기화하는 기존 동작도 그대로입니다.

## 4. 시작 환경 점검

`run()`의 앞부분이 바뀌었습니다.

- **이전:** 서버 시간 → exchangeInfo → premiumIndex → fundingInfo → 24h 시세를 한 번에 하나씩 받았습니다.
- **이후:** 이 다섯을 동시에 보냅니다(`_f7_startup_checks`). 실거래 모드에서는 실거래 엔진 시작 직전에 포지션 모드·계정·포지션·미체결·알고 주문도 동시에 받습니다(`_f7_prefetch_account`).
- 항목별 소요 시간을 로그(`startup checks in … ms`)와 `/health`(`startup_ms`)에 남깁니다.
- 실패 처리는 예전과 같습니다. 시간 동기화나 exchangeInfo가 실패하면 시작이 실패하고, 펀딩 일정 실패는 로그만 남깁니다.

모의 REST(요청마다 0.4초)로 잰 결과입니다.

| 단계 | 이전 | 이후 |
|---|---|---|
| 시장 점검 | 2.00초 | 0.40초 |
| 실거래 계정 점검(LiveAccount.start + 엔진 시작 + reconcile 읽기) | 2.81초 | 1.62초 |
| 합계 | 4.81초 | 2.02초 |

- 계정 쪽에 남은 0.8초는 `LiveAccount.start`의 자체 시간 동기화와 엔진 시작의 두 번째 계정 조회입니다. exchange/live.py와 execution 패키지는 이번 범위 밖입니다.
- 리플레이·페이퍼 시작 경로는 그대로 동작합니다. 리플레이의 REST는 로컬 응답이라 미리 받기를 건너뜁니다.

## 5. 지연 예산

`heartless/util/perf.py`의 `LATENCY`가 엔진·단계별로 최근 4,096개 표본을 모으고 p50·p99·최대를 냅니다(ms).

| 단계 | 구간 |
|---|---|
| `close_to_recv` | 봉 마감(거래소 시각, 측정된 오프셋으로 보정) → 1분봉 수신 |
| `recv_to_features` | 수신 → 피처 갱신·커서 이동 완료 |
| `feature_update` | 피처 갱신만(증분 추가 또는 배치 재계산, 마이크로초 해상도) |
| `close_to_decision` | 봉 마감 → 엔진이 그 봉의 on_bar를 끝냄(결정과 그 결정의 주문 전송 포함) |
| `close_to_sent` | 봉 마감 → 그 봉에서 결정한 주문 요청이 나감 |
| `sent_to_ack` | 주문 요청 → 거래소(또는 페이퍼 시뮬레이터) 응답 |

- **접근자:** `perf.latency_snapshot()`(지연 예산 + 시계)과 `perf.LATENCY.lines()`(한국어 한 줄 요약)입니다.
- **`/health`:** `/health`는 `app.health`의 키를 모두 보여 주므로, 이 요약이 `latency` 줄에 나옵니다. 함께 나오는 줄은 `clock`, `features`, `runtime`, `startup_ms`, `orderbook`입니다. `app.health`의 F7 부분은 분당 한 번만 다시 계산합니다.
- **일일 보고:** formatter에 연결 한 줄이 필요합니다(9절).
- **리플레이:** 요약 JSON의 `perf`와 보고서의 `performance:` 절에 같은 값이 들어갑니다. 리플레이는 가상 시계라서 네트워크 단계는 0이고, 봇 자신의 처리 시간만 보입니다.

## 6. 리플레이 핫패스 프로파일

`heartless replay ... --profile`(`ReplayConfig.profile`)은 이벤트 루프 스레드를 cProfile로 재고, 자체 시간 상위 함수를 요약 JSON(`perf.profile`)과 보고서에 넣습니다. 작업 스레드의 일(재앵커, 리서치)은 포함되지 않습니다.

첫 프로파일에서 F7 자신의 낭비를 하나 찾아 고쳤습니다. 합성 데이터 1일·2종목 리플레이 기준입니다.

- **증상:** 스케줄러가 5초마다 `app.health`를 갱신하면서, 지연 표본 저장소를 매번 정렬했습니다(`sorted` 15.6만 회). 같은 때 설치되지 않은 uvloop import도 매번 다시 시도했습니다(`find_spec` 12만 회).
- **고친 것:** F7 health는 분당 1회만 계산하고, uvloop 조회 결과는 캐시합니다.
- **결과:** 벽시계 23초 → 11초.

실데이터 리플레이도 한 번씩 돌렸습니다. 조건은 연구 DB(읽기 전용 원본), 2026-09-01 하루, 4종목(BTC·ETH·SOL·XRP), 운영 창 크기, 시드 25일, 출하 기본값입니다. 두 실행 모두 다른 작업과 CPU를 나눠 쓴 상태라 벽시계는 참고값입니다.

| 경로 | 벽시계 | 피처 갱신 p50 / p99 | RSS 끝 |
|---|---|---|---|
| `INCREMENTAL_FEATURES=false` | 290초 | 9.74 / 33.0 ms | 131 MB |
| 증분 + 오더북 대용치 + `--profile` | 178초 | 0.36 / 2.5 ms (프로파일 부하 포함) | 129 MB |

- 증분 실행에서는 재앵커 52회가 모두 배치 점검을 통과했고, 불변식 위반은 0건이었습니다.
- 프로파일에서 이벤트 루프 스레드의 가장 큰 CPU 항목은 SQLite입니다. `execute` 8.1만 회에 24초가 걸렸고, 봉마다 약 14회의 저장소 쓰기가 있습니다.
- 피처 증분 추가는 7,420회에 2.0초(누적)였습니다.
- 나머지 대부분(131초)은 작업 스레드(시작 시 컨텍스트 채우기 등)를 기다린 시간입니다.
- 다음 최적화 후보는 저장소 쓰기 묶기입니다(9절).

## 7. 설정

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `INCREMENTAL_FEATURES` | `true` | 운영 피처 프레임 증분 갱신. `false`면 이전의 매 봉 배치 재계산 |
| `ORDERBOOK_STREAM` | `false` | 로컬 오더북과 `ctx.book`(F-wave 연구가 쓸 때까지 꺼 둠) |
| `ORDERBOOK_MODE` | `partial` | `partial`(depth20) / `diff`(diff-depth + 스냅샷) |
| `ORDERBOOK_SPEED_MS` | `100` | 100 / 250 / 500 (가장 가까운 값으로 맞춤) |
| `ORDERBOOK_DEPTH_BPS` | `10` | 깊이·불균형을 재는 중간가 기준 범위 k |
| `CLOCK_DRIFT_WARN_MS` | `1000` | 시계 드리프트 경고 기준 |

선택 설치 패키지는 `pip install orjson uvloop`입니다. 둘 다 없어도 모든 기능이 같게 동작합니다.

## 8. 메모리

- 종목당 피처 프레임이 1.90 MB에서 2.27 MB가 되었습니다(+19%).
  - 재앵커까지 붙는 행
  - 숨은 열(로그 수익률, q-합, 테이커 매수량)
  - 미리 잡은 버퍼
- 200종목이면 약 +74 MB입니다.
- 합성 데이터 1일·2종목 리플레이(테스트용 짧은 창, 프로파일 없음):

|---|---|---|---|
| `INCREMENTAL_FEATURES=false` | 17초 | 107 MB | 2.81 / 11.6 ms |
| 증분(기본) | 6초 | 105 MB | 0.25 / 4.8 ms |

  이 리플레이는 창이 짧아(240봉) 배치 비용이 운영보다 작습니다. 운영 창(1,500봉)에서는 0절의 차이가 납니다.

## 9. 다른 패키지에 필요한 연결 (이번 패키지 범위 밖)

1. **uvloop 진입점**(`heartless/cli.py` `_run`)
   - 바꿀 줄: `asyncio.run(runner())` → `asyncio.run(runner(), loop_factory=perf.loop_factory())`
   - 필요한 import: `from heartless.util import perf`
2. **`Context.book` 필드**(`heartless/strategy/base.py`)
   - 추가할 줄: `book: BookFeatures = EMPTY_BOOK`
   - 지금은 운영 앱이 생성된 컨텍스트에 속성으로 붙입니다. 알파는 `book_of(ctx)`로 읽으면 어디서나 안전합니다.
3. **백테스터 대용치**(`heartless/learning/backtester.py`, 컨텍스트를 만드는 곳)
   - 추가할 줄: `ctx.book = proxy_from_frame(view.frames["1m"], t, settings.orderbook_depth_bps, info.tick_size)`
   - 운영 리플레이와 같은 대용치가 됩니다. lab 결과가 바뀌지 않도록 그 알파가 `book`을 읽을 때만 의미가 있습니다.
4. **일일 보고**(`heartless/notify/formatter.py` `fmt_daily`)
   - 추가할 줄: `lines.append(f"지연 예산: {esc(st.get('health', {}).get('latency', '-'))}")`
   - `status()`가 `health`를 이미 싣고 있습니다.
5. **실거래 진입 보류 규칙**(Wave F 계획): 호가 급변(스프레드 > 기준, 깊이 부족) 시 진입 보류. engine 패키지에서 `book_of(ctx)`로 구현합니다. 백테스트는 같은 규칙을 대용치에 적용합니다.
6. **저장소 쓰기 묶기**(`heartless/core/store.py`, app의 봉 저장): 실데이터 리플레이 프로파일에서 이벤트 루프의 가장 큰 CPU 항목이었습니다(6절).
7. **1시간 창 확대 검토**: 1h.ema200이 백테스터와 약 5e-4 차이 납니다(1.5절). 증분 갱신 덕분에 `LIVE_WINDOW["1h"]`를 늘리는 비용은 메모리와 1분봉 보관 일수뿐입니다.
